## 1. Planning -> DAG
Sources:
- Cognition, Don't Build Multi-Agents: https://cognition.ai/blog/dont-build-multi-agents  (principles: share full context; actions imply decisions -> parallel writers make conflicting implicit decisions)
- Cognition, Multi-Agents: What's Actually Working: https://cognition.com/blog/multi-agents-working  (single-writer; generator/verifier loop; reviewer with FRESH context outperforms; Devin Review ~2 bugs/PR, 58% severe)
- Anthropic multi-agent research system: https://www.anthropic.com/engineering/multi-agent-research-system  (15x tokens; poor fit when agents share context / many dependencies; vague task descriptions cause duplicated work -> give each subagent objective, output format, tool guidance, boundaries)
- LLMCompiler (planner + task fetching unit + executor, DAG of calls): https://arxiv.org/abs/2312.04511
- Kiro parallel task waves: https://kiro.dev/changelog/ide/0-12/ (independent tasks grouped into waves)
- CCPM (automazeio/ccpm): per-task metadata acceptance criteria, effort, depends_on, parallel, conflicts_with. https://github.com/automazeio/ccpm
- Taskmaster AI (eyaltoledano/claude-task-master): tasks.json with deps, priority, subtasks, "expand" step for complexity.
- Parallel-agent conflict data (secondary blog/arXiv summaries, verify): AgenticFlict (Apr 2026) ~27.7% of agent PRs conflict; CooperBench (Jan 2026) ~30% success drop when two agents collaborate; file-level ownership gave 100% auto-merge on 5 PRs but does not guarantee semantic correctness. https://codex.danielvaughan.com/2026/06/06/multi-agent-coordination-problem-concurrent-agents-semantic-conflicts-codex-cli/ , https://dev.to/aviad_rozenhek_cba37e0660/zero-conflict-architecture-the-8020-of-parallel-development-5aok
- Claim-plane / pre-write admission control: https://codex.danielvaughan.com/2026/07/28/claim-plane-pre-write-admission-control-parallel-coding-agents-codex-cli-changeintent-scope-promotion/

Takeaways:
- Parallelism helps only when tasks are truly decoupled in files AND decisions. Cognition's lesson: shared decisions (naming, interfaces, types) must be made BEFORE fan-out. So plan should include a "contracts first" root task (types/interfaces/schema/migrations/stub signatures) and fan out from it.
- Every worker gets the full plan summary + its node + upstream task summaries/diffs, not just a one-line subtask.
- Granularity: a task = one agent session that fits comfortably in context, ~1-5 files / <~400 changed LOC, independently verifiable (has a command that fails before and passes after). Too fine -> overhead and interface churn; too coarse -> no parallelism, context rot. Prefer wide shallow DAGs: 1 contracts node -> N leaf nodes -> 1 integration/glue node.
- Plan-time overlap detection: planner declares `touches` (globs, with intent read|write|create). Orchestrator (deterministic code, not LLM) computes pairwise write-set overlap among nodes that are not ordered by dependency; overlapping pairs get an added edge (serialize) or a "shared-file owner" node, or are merged. Hot files (package.json, lockfile, routes index, barrel index.ts, schema) -> assign to a single owner task or a final "wiring" task. Validate touches against repo (globs resolve, files exist) and optionally let planner explore repo with read-only tools. After execution compare actual diff vs declared touches; out-of-scope writes flagged (soft: warn + reviewer sees it; hard: reject).
- Validate DAG deterministically: acyclic, ids unique, depends_on resolve, every acceptance criterion maps to a verify command or review check, every plan requirement covered by >=1 task.
- Use structured output (JSON schema) for plan; keep plan as human-editable (UI) before execution = human checkpoint #1.

### Proposed task node schema
```
TaskNode {
  id: string            // "t3"
  title: string
  goal: string          // 2-5 sentences, what and why
  kind: "contracts"|"feature"|"test"|"refactor"|"docs"|"integration"
  depends_on: string[]
  acceptance_criteria: {id, text, verify?: {cmd: string, expect?: "exit0"|regex}}[]
  touches: {path_glob: string, mode: "create"|"modify"|"read"}[]   // write-set = create|modify
  out_of_scope: string[]      // explicit non-goals / files not to touch
  size: "S"|"M"|"L"           // L => planner must split
  verification: {setup?: string[], commands: string[]}  // lint/typecheck/unit tests scoped to touched area
  context_hints: {files_to_read: string[], docs: string[], symbols: string[], notes: string}
  interfaces: {provides: string[], consumes: string[]}  // named contracts (type names/fn signatures) for cross-task consistency
  agent_hint?: {engine: "claude"|"codex", model?, effort?}
  review: {reviewer_engine?: string, focus?: string[]}
  risk?: "low"|"med"|"high"   // high => human gate
}
Plan { summary, assumptions, open_questions, nodes[], global_verification: string[] , base_ref }
```

## 2. Scheduling
- Ready set = nodes with all deps `merged` (integration-merged), not merely `done`. Dispatch by priority = longest remaining critical path (sum of estimated sizes downstream), tie-break by fan-out, then by risk (do risky early). Concurrency limit global (default 3-4; bounded by API rate limits, CPU/RAM, and user's tokens), plus per-engine limit.
- What a dependent starts FROM: [exp, recommended] branch from the integration branch HEAD at the moment all its deps have been merged into it (so it sees merged dependency code, tests, and lockfile changes). Do NOT branch from a single dep's branch (diamond deps break) and do not branch from base (misses upstream APIs). Record `start_sha`. Tasks with no deps start from base (or from the integration branch current HEAD - slightly better because later rebase is trivial, but non-deterministic; pick base for roots, integration HEAD for dependents).
- Pipeline per node: queued -> provisioning -> running -> verifying -> reviewing -> (fix loop) -> approved -> merging -> merged | failed | blocked | cancelled | skipped.
- Failure: attempt-level retry (fresh worktree reset to start_sha, new attempt record, feed previous failure summary), max attempts N=2-3, maybe escalate model on last attempt. After exhaustion: node=failed; downstream nodes=blocked (not cancelled automatically); unrelated branches continue. Offer user: retry, edit task, re-plan subtree (planner gets failure log + current integration state, emits replacement subgraph; orchestrator diffs old/new DAG, cancels removed nodes), skip (mark satisfied if downstream can proceed), abort run.
- Cancel: SIGTERM agent process tree, keep worktree + transcript for forensics, mark cancelled, cascade to transitive dependents unless they are re-parented.
- Re-plan mid-flight only at node boundaries; never mutate running nodes; version plans (plan_version) and keep history.
- Human checkpoints (configurable): plan approval (default on), per-risk-high node approval before merge, conflict-resolution escalation, final PR review before push (default on), budget/cost threshold, repeated failures.
- Rate limit / auth errors from agents: treat as transient, pause scheduler (global backoff) rather than burning attempts.

## 3. Git isolation
Sources: git-worktree manual https://man7.org/linux/man-pages/man1/git-worktree.1.html ; Conductor scripts https://docs.conductor.build/core/scripts , https://docs.conductor.build/guides/how-to-setup ; worktree+AI conflict notes https://www.termdock.com/blog/git-worktree-conflicts-ai-agents
Conductor facts [src]: conductor.json at repo root; setup script runs per workspace creation (install deps, copy/symlink untracked files e.g. `ln -s "$CONDUCTOR_ROOT_PATH/.env" .env`), run script (uses $CONDUCTOR_PORT), archive script, optional nonconcurrent run mode. Each workspace = worktree + branch.

- Layout [exp]: worktrees OUTSIDE the repo, under app data or a sibling dir, e.g. `~/Library/Application Support/Legion/worktrees/<repo-hash>/<run-id>/<task-id>/` (or user-configurable `<repo>/../.legion-worktrees/`). Avoid inside repo (tools/watchers/tsc/eslint glob into it; .gitignore dance). Integration worktree: `.../<run-id>/_integration`. Branches: `legion/<run-short>/<task-id>-<slug>`, integration `legion/<run-short>/integration`. Attempt retries reuse the branch name but reset; or `-a2` suffix.
- Create: `git worktree add -b <branch> <path> <start-sha>` (always new branch per worktree: the same branch cannot be checked out in two worktrees). Detached heads are fine for scratch. `git worktree lock --reason "legion run X"` while a run is active so `prune` won't drop entries; `git worktree remove --force` then `git branch -D` and `git worktree prune` at cleanup; on app startup reconcile `git worktree list --porcelain` vs DB (orphans). Keep worktrees of failed tasks until user archives.
- Shared object store: all worktrees share .git objects/refs/config; fast & cheap, but: concurrent git operations contend on ref/packed-refs locks (retry on `index.lock`/`ref lock`; per-worktree index is separate so index.lock issues are rare across worktrees); `git gc` auto may run concurrently (set gc.auto=0 for runs or run gc at idle); hooks and config are shared (core.hooksPath husky hooks will fire in worktrees — decide to set `core.hooksPath=/dev/null` or use `--no-verify` for agent commits); submodules in worktrees are poorly supported; sparse-checkout is per-worktree; LFS works but smudge happens per worktree. Do not run `git checkout <branch>` in the user's main checkout — never touch it; treat user's main worktree as read-only (fetch only).
- Untracked env files: do not use git for them. Per-repo config lists `copy`/`symlink` globs (.env, .env.local, .npmrc, certs). Prefer COPY for files that agents might edit, symlink for read-only secrets. Mirror Conductor's `$CONDUCTOR_ROOT_PATH`-style env vars (LEGION_ROOT_PATH, LEGION_TASK_ID, LEGION_PORT_BASE).
- Dependencies: options in order of speed: (a) pnpm with global content-addressable store: `pnpm install --offline --frozen-lockfile` per worktree ~seconds, hardlinks; (b) macOS APFS clone of main checkout's node_modules: `cp -cR node_modules <wt>/node_modules` (clonefile, copy-on-write, near-instant, no space cost until modified) — caveat: only valid when lockfile identical to the source; native modules with absolute paths and `.bin` symlinks are OK with cp -c -R (preserves symlinks); pnpm's node_modules uses symlinks into `.pnpm` within same dir so relative links survive; (c) symlink node_modules to shared (fast but agents mutating it corrupt all; breaks bundlers resolving realpath outside root; dangerous) — avoid; (d) full install. Recommendation: per-repo setup script with Legion-provided helpers; default strategy auto-detect: lockfile -> pnpm/yarn/npm, try APFS clone from a "warm" template dir keyed by lockfile hash, then run `install --frozen-lockfile --prefer-offline` to reconcile. Re-run install in dependents when lockfile changed upstream. Build caches (.next, .turbo, tsbuildinfo) can be cloned too but may be stale—exclude.
- Ports: allocate each task a port block (e.g. base 40000 + 20*slot) exported as env `PORT`, `LEGION_PORT_0..n`; check free via bind test; repos' run scripts must read $PORT (Conductor does same). Also isolate DBs (sqlite path per worktree, docker compose project name `-p legion-<task>`), tmp dirs, and browser profiles. Most verify commands (unit tests) need no ports; e2e/dev servers serialise through a semaphore.
- Setup/teardown: `legion.json` (or .legion/config.json) per repo: `setup` (array of shell cmds), `verify` default commands, `teardown`/archive, `copy`, `ports`, `env`, `concurrency`. Run in worktree with timeout, stream logs into events, failure = node `provisioning_failed` (not an agent failure).
- Containers vs worktrees: worktrees = fast, native tooling, macOS-native, GUI-friendly, but weak isolation (agent can `cd ..`, touch global state, share ports/DBs/home dir, read secrets). Containers (Docker/devcontainer/Apple container) = strong sandbox, reproducible env, parallel DB/ports for free, but slow on macOS bind mounts, heavy images, auth for Claude/Codex needs passthrough, can't run macOS-specific tooling. Recommendation: worktrees by default + agent-native sandboxing (Claude Code sandbox/permission settings, Codex `workspace-write` sandbox with seatbelt) restricted to the worktree path; optional per-repo container mode later (mount worktree into container, same git logic).

## 4. Integration / merge
Sources: git-merge-tree https://git-scm.com/docs/git-merge-tree ; stacked tools: Graphite (graphite.dev), git-spice (abhinav.github.io/git-spice), git-town, Sapling [exp on details].
- `git merge-tree --write-tree <branch1> <branch2>` (Git >= 2.38) performs a real merge in the object DB only; exit 0 clean, 1 conflicted; outputs result tree OID then conflicted-file info (`--name-only`, `-z` for machine parsing; `--merge-base=` for explicit base). Use: (1) at plan/runtime to predict whether finished task branch X merges cleanly into integration HEAD before touching any worktree; (2) pairwise check of in-flight branches to detect early divergence (compare running tasks' current HEADs, warn/serialize). Result tree can be turned into a commit via `git commit-tree` for cheap clean merges (no worktree needed at all!). Bundled git on mac may be old: require git >= 2.38, check at startup.
- Recommended strategy [exp]: ONE integration branch `legion/<run>/integration` in its own worktree. When a task passes review: (1) predict with merge-tree; (2) if clean: `git merge --no-ff -m "task <id>: <title>" <task-branch>` in the integration worktree (or commit-tree route); (3) run the repo's verify (typecheck + tests affected, or full) on the integration worktree — "post-merge verification" — because textually clean != semantically clean; (4) failure -> reset integration to previous SHA (`git reset --hard` in integration worktree, which is ours), mark task `merge_failed`, spawn a fixer attempt in the task worktree that first merges the integration HEAD into the task branch (update from integration, not rebase, to preserve review state) and resolves/fixes. Serialize merges via a single merge queue (mutex), in completion order constrained by topological order (dependents only merge after deps merged, guaranteed by scheduling).
- Merge vs rebase vs squash: task branches keep granular agent commits; integrate with `--no-ff` merge commits (preserves task boundaries, easy to revert a task, rerere-friendly), final PR merged by user's choice (GitHub "squash and merge" typically). Alternative: squash each task into one commit on integration so PR history = one commit per task (cleaner for reviewers; and good if agent commits are noisy). Recommend: setting `integration.mode: squash-per-task (default) | merge-commits`. Avoid rebase of shared branches; rebase only task branches pre-review if base moved and only if no one else holds them. Octopus merges: refuse on any conflict, poor error attribution, no benefit — avoid. Merge queue (GitHub merge queue) is a remote CI-side concept; Legion's local serialized queue is its analogue.
- Conflict resolution agent: input = both task specs (goal + acceptance criteria), both diffs summary, `git merge-tree` conflict list, conflict markers in a scratch merge in the task worktree (merge integration HEAD into task branch). Instructions: preserve intent of BOTH; don't drop either side's tests; run verification; output structured result {resolved_files, decisions, concerns}. After resolution a reviewer re-checks the merge commit diff (`git diff integration...HEAD` plus conflict-region diff using `git show --remerge-diff <merge>` (git >= 2.36) which shows how conflicts were resolved). Escalate to human after 2 failures. 
- `git rerere`: enable in integration and task worktrees (`rerere.enabled=true`; the rr-cache lives in the shared common dir so resolutions are reusable across worktrees; useful when retrying merges after reset). Cheap win, enable by default.
- Lockfiles/generated files: never LLM-merge; use merge drivers or "take either side then regenerate" (`pnpm install` to regenerate lockfile, codegen commands) — configurable `regenerate` commands per path glob.
- Stacked branches vs single PR: Graphite/git-spice/git-town/Sapling model a linear stack of dependent PRs (restack on change). A DAG is not a stack; only chains map cleanly. Single PR from integration branch is the default (matches the stated workflow, one review surface, atomic). Optional stacked mode: linearize the DAG by topological order into a chain (each branch based on previous), or per-chain; heavy restack complexity — treat as v2, implement via git-spice/gt CLI if installed rather than reimplementing.
- Final holistic checks on integration branch: full test/lint/typecheck/build, a holistic review agent over `base...integration` diff vs original issue/plan acceptance, then optional human gate.

## 5. Review
Sources: Cognition clean-context review https://cognition.com/blog/multi-agents-working ; OpenAI Codex review (`codex exec` with review prompt / `/review`; `codex exec --output-schema` for structured JSON) [exp, verify against current docs]; Claude Code headless `claude -p --output-format json --json-schema` [exp, verify].
- Reviewer = fresh session, different engine from author by default (Claude authored -> Codex reviews and vice versa; fall back to same engine with different model/fresh context if only one is configured). Rationale: Cognition shows clean-context reviewers outperform; cross-model diversity reduces correlated blind spots [exp].
- Reviewer inputs: task spec (goal, acceptance criteria, out_of_scope, touches), plan summary, original issue, diff vs the task's start_sha, verification results (commands, exit codes, truncated logs), declared-vs-actual touch set report, upstream task summaries. Reviewer has read-only repo access + may re-run tests; must not edit.
- Structured output:
```
Review { verdict: "approve"|"request_changes"|"reject_replan",
  criteria: [{id, status: "met"|"unmet"|"unverifiable", evidence}],
  findings: [{severity: "blocker"|"major"|"minor"|"nit", file, line, category: "correctness"|"security"|"tests"|"scope"|"style", description, suggested_fix}],
  summary }
```
  Gate: approve iff all criteria met and zero blocker/major; minors/nits are recorded (pass into PR notes) not looped on. Enforce schema; on invalid output retry once.
- Fix loop: request_changes -> author agent resumes (same session if possible) given only blocker/major findings (Cognition: author should filter, avoid scope creep) -> re-verify -> re-review (new reviewer session). Max iterations 2-3; then escalate (human, or re-plan). Detect oscillation (same finding repeats) and stop.
- Deterministic gates BEFORE the LLM reviewer: tests/lint/typecheck pass, diff non-empty, no writes outside touches (or flagged), no secrets in diff, no modified lockfiles unexpectedly.
- Final holistic review of integration branch: different prompt (coherence, duplicated helpers, interface consistency, missing wiring, issue requirement coverage); findings -> either a generated "fixup" task appended to DAG (run through the same pipeline) or surfaced to the human.
- Human gates: per-node optional approval, final PR gate. UI should show diff, review findings, logs, and allow "send back with comment" (comment becomes a finding).

## 6. PR creation
Sources: gh manual https://cli.github.com/manual/gh_pr_create [exp on flags, standard].
- `git push -u origin legion/<run>/integration` (consider a nicer user-facing branch name, `legion/<slug>`; offer push to fork).
- `gh pr create --base <base> --head <branch> --title "..." --body-file body.md [--draft] [--label ..] [--reviewer ..] [--assignee @me] [--milestone ..] [--project ..]`. Use `--body-file` (avoid shell quoting). `--draft` default recommended (human promotes). `gh pr create --fill` is not useful; `--dry-run` exists for preview. Capture URL from stdout; then `gh pr view --json number,url`. Alternative: Octokit REST with token from `gh auth token`.
- Linking issues: put `Closes #123` / `Fixes owner/repo#123` in body (GitHub auto-closes on merge into default branch). Linear: include issue ID (e.g. `Fixes ENG-123` or branch name containing the ID) — Linear's GitHub integration links via branch name, PR title, or magic words; Linear branch-name helper gives `user/eng-123-title`. Optionally name the integration branch from the Linear/GitHub branch suggestion.
- Body generated by an agent (or template + LLM summary) from: original issue, plan summary, per-task table (title, status, review verdict, files), verification results (commands + pass), notable decisions/assumptions/open questions, conflicts resolved, unresolved nits, link to Legion run id. Keep <~ 65k chars (GitHub body limit 65,536). Title <70 chars, conventional-commit style if repo uses it. Respect `.github/pull_request_template.md` (read and fill it).
- Stacked mode (optional): one PR per task or chain, each with `--base` = previous branch; use Graphite `gt submit` / git-spice `gs stack submit` if available. Default single PR.

## 7. State model
- Persist (SQLite via better-sqlite3 in main process, WAL mode): runs(id, repo, base_ref, base_sha, issue_ref, status, config_json, created_at), plans(run_id, version, json, status, author_attempt), tasks(run_id, plan_version, node_id, spec_json, status, depends_on, branch, worktree_path, start_sha, head_sha, merged_sha), attempts(task_id, n, role: author|reviewer|conflict_resolver|planner, engine, model, session_id, pid, status, started/ended, exit_reason, cost/tokens, worktree/branch), reviews(attempt_id, verdict, json), events(seq, run_id, task_id, attempt_id, ts, type, payload_json) append-only, artifacts(id, attempt_id, kind: transcript|diff|log|verify_result|pr_body, path, sha256), pr(run_id, url, number, state).
- Large blobs (transcripts, logs, diffs) on disk under run dir, referenced from artifacts.
- Event sourcing vs tables: recommended hybrid [exp] — current-state tables are the source of truth for the scheduler (simple, queryable, transactional), plus an append-only events table written in the same transaction for UI timeline, audit, debugging, and replays. Full event sourcing (derive state by folding) adds projection complexity not needed here. Workflow engines (Temporal etc.) overkill for desktop.
- Crash recovery: on startup, load runs in non-terminal states; for each `running` attempt, check pid alive (and session id); if dead mark `interrupted`; reconcile worktrees (`git worktree list`) and branch heads vs DB; resume agent sessions if engine supports (Claude `--resume <session_id>`, Codex `codex exec resume`) [exp, verify], else start new attempt from last committed state in worktree (agents should commit early/often; orchestrator auto-commits WIP checkpoints on a separate ref). Make every scheduler transition idempotent and recorded with state-machine guards (CAS update `WHERE status=?`). Merge step: record `intent` (pre-merge integration SHA) before merging so interrupted merges can be rolled back/continued. Never rely on in-memory state.
- Agent processes: spawn detached? On Electron quit, either terminate children and mark interrupted or keep in utility process; simplest: run orchestrator in a separate Node utility process/daemon so UI reloads don't kill runs.
- Idempotent cleanup: worktree removal is a final state transition (`archived`).

## Cross-cutting recommendations (summary)
1. Contracts-first DAG + deterministic overlap analysis (touches) + serialize overlapping writers.
2. Dependents branch from integration HEAD once deps merged.
3. Single integration branch, serial merge queue, post-merge verification, merge-tree prediction, rerere on.
4. Cross-engine fresh-context reviewer, structured verdict, <=2-3 fix loops, then escalate.
5. Draft PR via gh --body-file; stacked PRs v2.
6. SQLite current-state + append-only events.
