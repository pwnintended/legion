# Driving OpenAI Codex programmatically from Legion (Electron host)

Verified 2026-10-06 against codex-cli 0.160.0 (/opt/homebrew/bin/codex), @openai/codex-sdk 0.160.1 (npm latest; alpha 0.162.0-alpha.16), and live runs on this machine (ChatGPT "pro" login, default model `gpt-6.1-sol`).
Legend: [V] = verified by running the binary / reading generated schema; [D] = from docs only (docs now live at learn.chatgpt.com/docs/*, developers.openai.com/codex/* 308-redirects there); [?] = unverified.

Tip for tooling: `codex <sub> --help` fails with "stdin is not a terminal" when no TTY and stdin is not /dev/null; use `codex help <sub>` or `</dev/null`. Also `codex exec` prints "Reading additional input from stdin..." unless stdin is closed (`</dev/null` or pass prompt and `stdin: 'ignore'`).

## 1. Integration options

| Option | What it is | Verdict |
|---|---|---|
| `@openai/codex-sdk` | Thin TS wrapper that SPAWNS `codex exec --experimental-json [resume <id>] --output-schema <tmpfile>` and parses JSONL [V: dist/index.js lines 177-263]. Depends on `@openai/codex` (bundled binary). API: `new Codex({codexPathOverride, baseUrl, apiKey, config, env})`, `startThread(opts)`, `resumeThread(id, opts)`, `thread.run(input,{outputSchema,signal})`, `thread.runStreamed()` -> `{events}`. ThreadOptions: model, sandboxMode, workingDirectory, skipGitRepoCheck, modelReasoningEffort (`minimal..xhigh,max,ultra,persistent`), networkAccessEnabled, webSearchMode, approvalPolicy, additionalDirectories. | Good for fire-and-forget headless runs. NO approval round-trips, no steer, no live-takeover, no dynamic tools. Equivalent to `exec --json`. |
| `codex exec --json` | One-shot JSONL stream on stdout; `exec resume <id\|--last>`, `exec fork`, `exec review`; `--output-schema`, `-o <file>`, `--ephemeral`, `--skip-git-repo-check`, `--ignore-user-config`, `--ignore-rules`. | Simple + robust for planning/review/non-interactive tasks (set approval `never`). | `codex mcp-server` | Documented historically. In 0.160.0 `codex mcp-server` is NOT a subcommand (it is treated as a prompt and launches the TUI!) and `codex help mcp-server` errors. [V] | Do not use. Use app-server. (Possibly moved/removed; [?] check `codex help` in future versions.) |
| TUI in PTY (node-pty + xterm.js) | `codex [PROMPT]`, `codex resume <id>`, `codex fork`. ### Live view + human takeover (recommended design)
- Run ONE `codex app-server` (stdio child per Legion, or shared). The CLI also supports a shared local daemon: `codex app-server daemon start|stop|restart|version`, socket `~/.codex/app-server-control/app-server-control.sock`, `codex agents` (browse all sessions on the daemon), `codex queue --thread <id> --message <text>` (queue a message to an existing session). [V help text]
- TUI can attach to a server: `codex --remote ws://host:port|unix://PATH [--remote-auth-token-env VAR]` and `codex resume/fork --remote`. App-server flags: `--listen ws://127.0.0.1:4500`, `--ws-auth capability-token|signed-bearer-token`, `--ws-token-file`, `--ws-token-sha256`, `--ws-shared-secret-file`, `--ws-issuer`, `--ws-audience`. [V help; D docs: plain ws only for localhost/ssh forward]. So the pattern is: Legion runs `codex app-server --listen unix://<path>` (or ws loopback + capability token), drives agents with JSON-RPC itself, and a "Take over" button spawns a PTY running `codex resume <threadId> --remote <addr>` (xterm.js in a pane) against the same server. [?] I did NOT live-test two clients (Legion + TUI) on the same thread; confirm multi-client subscription semantics (`thread/resume` on a running thread "rejoins" it per the schema doc comment) and that Legion pauses its own driving while the human types. Fallback: interrupt turn, kill app-server connection, `codex resume <id>` in PTY (rollout is on disk), then on exit resume via `thread/resume`.
- Alternative cheap takeover: since rollouts persist, "take over" = stop the turn (`turn/interrupt`), open PTY `codex resume <id> -C <worktree>`; on close, `thread/resume` and continue.

## 2. Event stream shape

### app-server (JSON-RPC, verified live)
Handshake: request `initialize {clientInfo:{name,title,version}, capabilities:{experimentalApi:bool, requestAttestation:false, optOutNotificationMethods?:[..]}}` -> response `{userAgent, codexHome, platformFamily, platformOs}`; then notification `{"method":"initialized"}`. Messages are JSONL (no `jsonrpc` field needed). Server notifies `remoteControl/status/changed` etc. Set `clientInfo.name` to Legion (docs: first-party/desktop integrations should contact OpenAI for registration).

Client requests (selected, from generated ClientRequest): `thread/start|resume|fork|read|list|loaded/list|archive|unarchive|delete|name/set|metadata/update|compact/start|revert|turns/list|items/list|unsubscribe|inject_items|shellCommand|goal/{get,set,clear}|attachment/*`, `thread/settings/update`(experimental), `turn/start|steer|interrupt`, `review/start`, `model/list`, `account/{read,login/start,logout,rateLimits/read,usage/read}`, `config/{read,value/write,batchWrite,mcpServer/reload}`, `mcpServerStatus/list`, `mcpServer/tool/call`, `skills/list`, `hooks/list`, `command/exec` (+write/resize/terminate for PTY), `fs/*`, `permissionProfile/list`, `configRequirements/read`, `gitDiffToRemote`.

Server notifications: `thread/started`, `thread/status/changed` (status: notLoaded|idle|systemError|active{activeFlags:[waitingOnApproval|waitingOnUserInput]}), `turn/started`, `turn/completed` (Turn{id,items,status completed|interrupted|failed|inProgress,error,startedAt,completedAt,durationMs}), `item/started`, `item/completed`, `item/agentMessage/delta`, `item/reasoning/{summaryTextDelta,summaryPartAdded,textDelta}`, `item/commandExecution/outputDelta`, `item/commandExecution/terminalInteraction`, `item/fileChange/{outputDelta,patchUpdated}`, `item/mcpToolCall/progress`, `item/plan/delta` (experimental), `turn/plan/updated {explanation, plan:[{step,status pending|inProgress|completed}]}`, `turn/diff/updated` (aggregated unified diff), `thread/tokenUsage/updated {total,last: {totalTokens,inputTokens,cachedInputTokens,cacheWriteInputTokens,outputTokens,reasoningOutputTokens}, modelContextWindow}`, `account/rateLimits/updated`, `hook/started|completed`, `serverRequest/resolved`, `thread/compacted`, `model/rerouted`, `warning`, `configWarning`, `deprecationNotice`, `error`, `item/autoApprovalReview/{started,completed}`, `thread/goal/updated`, `thread/queue/changed`.

ThreadItem types (v2): userMessage, hookPrompt, agentMessage{text, phase: commentary|final_answer}, plan{text}, reasoning{summary[],content[]}, commandExecution{command,cwd,status inProgress|completed|failed|declined,aggregatedOutput,exitCode,durationMs,commandActions[]}, fileChange{changes:[{path,kind,diff}],status}, mcpToolCall{server,tool,arguments,status,result,error,durationMs}, dynamicToolCall{namespace,tool,arguments,status,contentItems,success}, collabAgentToolCall / subAgentActivity (multi-agent), webSearch, imageView, imageGeneration, sleep, enteredReviewMode/exitedReviewMode{review}, contextCompaction, functionCallOutput.

Observed live order for a turn: `thread/status active` -> `turn/started` -> hook events (user's ~/.codex/hooks.json DID run; use `--ignore-user-config`/own CODEX_HOME if isolation wanted) -> item userMessage -> agentMessage(commentary) -> status `active[waitingOnApproval]` -> commandExecution item/started -> server REQUEST `item/commandExecution/requestApproval` -> `serverRequest/resolved` -> item/completed(status declined) -> tokenUsage/rateLimits updated -> agentMessage(final_answer) -> `thread/status idle` -> `turn/completed`.

### exec --json / SDK JSONL (verified live)
Events: `thread.started{thread_id}`, `turn.started`, `item.started|updated|completed{item}`, `turn.completed{usage:{input_tokens,cached_input_tokens,cache_write_input_tokens,output_tokens,reasoning_output_tokens}}`, `turn.failed{error}`, `error{message}`. Item types: `agent_message{text}`, `reasoning{text}`, `command_execution{command,aggregated_output,exit_code,status}`, `file_change{changes[{path,kind}],status}`, `mcp_tool_call{server,tool,arguments,result,error,status}`, `web_search{query}`, `todo_list{items[{text,completed}]}` (the agent's plan checklist), `error`. No deltas: agent text arrives complete.

Rendering guidance: activity feed from item.started/completed; live text from `item/agentMessage/delta` and `commandExecution/outputDelta`; plan checklist from `turn/plan/updated` (or `todo_list`); diff panel from `turn/diff/updated` or fileChange items; token/cost meter from `thread/tokenUsage/updated`; rate-limit gauge from `account/rateLimits/updated`; "needs you" badge from thread status `waitingOnApproval|waitingOnUserInput`.

## 3. Sandbox & approvals
- Sandbox modes [V]: `read-only`, `workspace-write`, `danger-full-access` (`-s/--sandbox`; thread/start `sandbox`; turn/start `sandboxPolicy` objects: `{type:"readOnly",networkAccess}`, `{type:"workspaceWrite",writableRoots[],networkAccess,excludeTmpdirEnvVar,excludeSlashTmp}`, `{type:"dangerFullAccess"}`, `{type:"externalSandbox",networkAccess}`). Network off by default in workspace-write; enable via `-c sandbox_workspace_write.network_access=true` [D]. Protected even inside writable roots: `.git`, `.agents/`, `.codex/` [D] -> consider consequences for Legion: agents inside a worktree cannot `git commit` under workspace-write if `.git` is read-only (the worktree's `.git` is a gitdir pointer file). [?] Not tested; plan for Legion (the orchestrator) to do commits/merges itself, or use danger-full-access in worktrees with Legion-side guards. macOS uses Seatbelt (`sandbox: "seatbelt"` seen in turn metadata).
- Approval policies: CLI 0.160 `-a` accepts only `on-request` and `never` [V help]. The app-server schema `AskForApproval` = `"untrusted" | "on-request" | {granular:{sandbox_approval,rules,skill_approval,request_permissions,mcp_elicitations}} | "never"` [V] — `on-failure` is gone from the app-server enum, though the SDK 0.160.1 type still lists `"on-failure"|"untrusted"`; docs say `untrusted` is retired and breaks startup config [D]. -> Legion should only use `on-request`, `never`, `granular`. My live test with `untrusted` over app-server DID work in 0.160.0 (approval request raised) [V] but don't rely on it.
- `--dangerously-bypass-approvals-and-sandbox` (`--yolo`), `--approve-for-me` (auto-review in workspace-write), `approvals_reviewer = "user" | "auto_review" | "guardian_subagent"` (subagent auto-approves low-risk escalations; emits `item/autoApprovalReview/*`).
- Approval over app-server [V live]: server sends JSON-RPC REQUEST (has `id`) :
  - `item/commandExecution/requestApproval` params `{kind, threadId, turnId, itemId, startedAtMs, approvalId?, environmentId, reason?, networkApprovalContext?, command, cwd, commandActions[], proposedExecpolicyAmendment?, proposedNetworkPolicyAmendments?}` -> reply `{decision: "accept"|"acceptForSession"|"decline"|"cancel"|{acceptWithExecpolicyAmendment:{execpolicy_amendment}}|{applyNetworkPolicyAmendment:{network_policy_amendment}}}`. `decline` = tell model no and continue; `cancel` = interrupt turn.
  - `item/fileChange/requestApproval` -> `{decision: accept|acceptForSession|decline|cancel}`
  - `item/permissions/requestApproval` (extra permissions profile), `mcpServer/elicitation/request`, `item/tool/requestUserInput` (experimental; questions[] -> `{answers:{id:{...}}}`; this is the model asking the human), `item/tool/call` (dynamic tool), `account/chatgptAuthTokens/refresh`, legacy `applyPatchApproval`/`execCommandApproval`.
  - Must answer by echoing the request `id`; `serverRequest/resolved` notification then fires. Until answered the thread has `activeFlags:["waitingOnApproval"]`.
- Policy for Legion: coding agents = `workspace-write` + `on-request` surfaced to GUI (or `never` for unattended); planner/reviewer = `read-only` + `never`.

## 4. Planning & structured output
- `--output-schema <file>` (exec, exec resume) / SDK `outputSchema` / app-server `turn/start.outputSchema` (per turn, JSON Schema) [V live]: final agent message is JSON text conforming to schema (OpenAI strict structured-output rules: `additionalProperties:false`, all properties `required`). Result arrives as final `agent_message` text; also `-o <file>`. My test returned `{"tasks":[{"id":"A","deps":[]},{"id":"B","deps":["A"]}]}`. Schema applies to that turn only. Tools can still be used before the final message.
- Plan features: `turn/plan/updated` / `todo_list` item = agent's own checklist (update_plan tool); ThreadItem `plan` + `item/plan/delta` (experimental) = "proposed plan" in Plan collaboration mode. Plan mode: `CollaborationMode {mode:"plan"|"default", settings:{model, reasoning_effort, developer_instructions|null}}` settable on `turn/start.collaborationMode` or `thread/settings/update` (EXPERIMENTAL; needs `experimentalApi:true`). `collaboration_modes` feature flag is "removed/true" (always on). In plan mode the model explores read-only and emits a `plan` item rather than editing. [?] Exact output text format of plan item not examined live.
- For Legion's DAG: simplest robust approach = planner turn in `read-only` with `outputSchema` describing `{tasks:[{id,title,description,deps[],files[],acceptance[]}]}`; optionally a first Plan-mode turn for human-readable plan, then second turn with outputSchema to convert to DAG.

## 5. Threads / sessions
- ID: UUIDv7 thread id (`01a112ee-...`); `sessionId == threadId` for root threads. Rollouts persisted at `~/.codex/sessions/YYYY/MM/DD/rollout-<local-ts>-<threadId>.jsonl` [V]; archived in `~/.codex/archived_sessions`; sqlite state/log DBs alongside (`goals_1.sqlite`, `logs_2.sqlite`). `$CODEX_HOME` relocates everything (auth.json lives there too) [D; observed `codexHome` in initialize]. `--ephemeral` / `ephemeral:true` = no persistence. New "paginated" history mode: use `thread/turns/list` + `thread/items/list`; `codex migrate-rollouts` exists for legacy files.
- Resume: CLI `codex exec resume <UUID|thread-name|--last> [PROMPT]` (note: resume re-takes -m, bypass flags, --json, --output-schema, but NOT -s/-C in its option list; per-run sandbox must be via `-c sandbox_mode=...`; [?] verify), TUI `codex resume`, SDK `resumeThread(id)`, app-server `thread/resume {threadId, overrides…, excludeTurns}`.
- Follow-up input: new `turn/start` on an idle thread; `turn/steer {threadId, input, expectedTurnId}` injects into the ACTIVE turn; `codex queue --thread X --message` / `thread/queue/changed` for queued messages. Interrupt: `turn/interrupt {threadId, turnId}` -> turn status `interrupted`. SDK: AbortSignal; exec: kill process (SIGINT).
- Fork: `thread/fork {threadId, lastTurnId?, overrides…}`, `codex fork`, `codex exec fork <id>`. Others: `thread/name/set`, `thread/rollback`-like `thread/revert`, `thread/compact/start`, `thread/archive`.

## 6. Working dir, worktrees, AGENTS.md, config
- `-C/--cd DIR`; app-server `cwd` (thread/start, turn/start; `runtimeWorkspaceRoots` experimental); `--add-dir DIR` extra writable roots; `--skip-git-repo-check` (exec); `--worktree` (NEW in 0.160: "Run the session in a new managed Git worktree") — but Legion should create worktrees itself for DAG control and pass `-C`.
- AGENTS.md: auto-loaded hierarchically from ~/.codex/AGENTS.md (exists here) and repo root down to cwd; per-thread extra instructions via app-server `baseInstructions`/`developerInstructions`. Codex also reads `.agents/`, `.codex/` (config, hooks, rules).
- Config: `~/.codex/config.toml`; `-c key=value` (TOML-parsed, dotted paths, repeatable; app-server: `config:{...}` JSON map on thread/start/resume/fork, and `-c` on `app-server` itself); `-p/--profile <name>` now layers `$CODEX_HOME/<name>.config.toml` ("CONFIG_PROFILE_V2"); `--ignore-user-config` (auth still from CODEX_HOME), `--ignore-rules`, `--strict-config`; `--enable/--disable <feature>`; project trust via `[projects."/path"] trust_level="trusted"` (untrusted projects may skip project config). Hooks and user config.toml from the user's real home will leak into Legion-driven runs (observed `hook/started` from ~/.codex/hooks.json) — decide whether to isolate with a Legion-owned `CODEX_HOME` (needs auth copied/logged in separately) or `--ignore-user-config`.

## 7. MCP for orchestrator tools
Verified live: per-run, no file edits needed:
```
codex exec --json -c 'mcp_servers.legion.command="node"' -c 'mcp_servers.legion.args=["/path/mcp.mjs"]' \
  -c 'mcp_servers.legion.default_tools_approval_mode="approve"' "..."
```
Codex launched my stdio MCP server, listed `report_progress`, model called it; JSONL showed `mcp_tool_call{server:"legion",tool:"report_progress",arguments,result}`; call `_meta` carried threadId/turnId/callId/sandbox/model metadata (handy for correlating tool calls with the right DAG task). Streamable-HTTP servers: `mcp_servers.x.url="http://127.0.0.1:PORT/mcp"` + `bearer_token_env_var` [D; `codex mcp add NAME --url URL --bearer-token-env-var VAR` / `-- cmd args` with `--env K=V`]. Other keys [D, unverified here]: `startup_timeout_sec`, `tool_timeout_sec`, `enabled_tools`, `disabled_tools`, `required`. Without `default_tools_approval_mode="approve"` MCP tool calls may trigger an approval/elicitation prompt (in exec they would auto-fail) [?]. With app-server, pass the same via `config:{mcp_servers:{legion:{url:...}}}` on thread/start (inline JSON; [?] untested), and `config/mcpServer/reload`.
Better for app-server: **dynamic tools** (`thread/start.dynamicTools:[{type:"function",name,description,inputSchema}]`, experimental): the model calls the tool, server sends REQUEST `item/tool/call {threadId,turnId,callId,tool,arguments}`, Legion replies `{contentItems:[{type:"inputText",text}],success:true}` — no separate MCP server process, in-process handlers for `report_progress`, `request_human_input`, `mark_task_done`. Persisted in rollout and restored on resume [D]. [?] not live-tested; fall back to a local MCP HTTP server embedded in the Electron main process (identical for Claude Code -> single implementation of the tool server; use per-task bearer token in URL/env to identify the task).

## 8. Models, effort, usage, limits
- `-m/--model`, config `model`, `model_reasoning_effort` (values by SDK: minimal|low|medium|high|xhigh|max|ultra|persistent; actual allowed set is per-model from `model/list` -> `supportedReasoningEfforts`). `model_reasoning_summary`, `service_tier` ("default"/fast), `personality` (deprecated). Local default here: `gpt-6.1-sol`, effort high. `--oss --local-provider lmstudio|ollama` for local models; custom `model_providers` in config.
- Usage: exec `turn.completed.usage` (per turn); app-server `thread/tokenUsage/updated` (total + last, context window) and `account/usage/read`. No dollar cost reported — compute from API pricing if on API key; with ChatGPT login it's plan-quota based.
- Rate limits: `account/rateLimits/read` + `account/rateLimits/updated` -> `{limitId, primary:{usedPercent,windowDurationMins,resetsAt}, secondary, credits:{hasCredits,unlimited,balance}, planType, rateLimitReachedType}`. Observed live: `primary usedPercent 73, 10080-min (weekly) window` on pro plan with credits balance. Legion should throttle DAG parallelism based on this and handle `error` notifications / `turn.failed` for limit reached (and `model/rerouted`).

## 9. Auth
- Two modes: ChatGPT sign-in (subscription; `codex login`, browser; `codex login --device-auth` headless beta) and API key (`codex login --with-api-key` reads stdin; env `OPENAI_API_KEY`/`CODEX_API_KEY` for exec; SDK `new Codex({apiKey})`). Also `codex login --with-access-token`, `codex login status` (returned "Logged in using ChatGPT"). Credentials: `$CODEX_HOME/auth.json` (maybe keyring) [D].
- app-server `account/login/start` types: `apiKey`, `chatgpt`, `chatgptDeviceCode`, `chatgptAuthTokens` (host app supplies accessToken+chatgptAccountId, and must answer server request `account/chatgptAuthTokens/refresh`), plus Bedrock variants. `account/read`, `account/updated {authMode:"chatgpt",planType:"pro"}` [V].
- Caveats for a third-party app: (a) simplest and most defensible = reuse the user's existing `codex login` state (Legion never touches tokens; spawn codex with the user's CODEX_HOME) or let user paste API key into Legion's keychain and pass via env. (b) `chatgptAuthTokens` lets host manage tokens, but Legion would need its own OAuth client — OpenAI docs say desktop integrations should contact OpenAI to register as known client [D, hedged]; avoid. (c) API-key mode: usage billing, some features reduced (e.g. some plugin/cloud features, fast tier) [D]. (d) Subscription limits are shared with the user's interactive Codex use and are weekly/5h-window based; heavy parallel DAGs can exhaust. (e) ToS for automated use of subscription via third-party app: [?] not verified; check OpenAI terms before shipping.

## 10. Built-in code review
- `codex review [PROMPT|-] [--uncommitted | --base BRANCH | --commit SHA [--title T]]` and `codex exec review ...` (also accepts `--json`, `--output-schema`, `--ephemeral`, `-o` per `exec review --help`). Not JSON by default. (`codex review` has no -C/-m/-s flags; run with cwd = worktree and use `-c model=...`.)

- For Legion, deterministic parsing is better: run a normal read-only turn (or `exec`) with your own review prompt + `outputSchema` {verdict, findings:[{severity,file,line,title,body}]}; optionally use `/review` prompt text as a template. Cross-backend: same reviewer schema for Claude.

## Recommended integration (summary)
1. Core adapter on `codex app-server` over stdio (one child process per Legion run or a shared daemon), typed with `codex app-server generate-ts --experimental` output pinned to the bundled codex version (ship the binary or check `codex --version` ≥ 0.160 at startup; protocol is "experimental").
2. Normalize events into Legion's own `AgentEvent` union (message delta, reasoning, command, file change, mcp/dynamic tool call, plan, usage, approval-request, status).
3. Planner/reviewer: app-server read-only turn with `outputSchema`; fallback `codex exec --json --output-schema` for a trivially simple backend path (SDK is equivalent; not worth the dependency since it can't approve/steer).
