## 1. Integration options

### A. Agent SDK (TypeScript) `query()` — RECOMMENDED for the headless/orchestrated path
- `import { query } from "@anthropic-ai/claude-agent-sdk"`. It spawns the bundled native `claude` binary (optional dep; override with `pathToClaudeCodeExecutable`, custom spawn with `spawnClaudeCodeProcess`, which matters for Electron: spawn from utility process / pass node/bun via `executable`, or point at the system `claude`). Under the hood it speaks the same stream-json control protocol as the CLI.
- `query({prompt: string | AsyncIterable<SDKUserMessage>, options})` returns `Query` (an AsyncGenerator<SDKMessage>) with control methods: `interrupt()`, `setPermissionMode()`, `setModel()`, `applyFlagSettings()`, `streamInput()`, `stopTask()`, `mcpServerStatus()`, `setMcpServers()`, `getContextUsage()`, `rewindFiles()`, `supportedModels()`, `accountInfo()`, `close()`.
- Streaming-input mode (AsyncIterable prompt) is the recommended mode: long-lived process, queued messages, interrupt, image input, canUseTool, in-process MCP servers. Single-string mode = one-shot, no mid-run injection. A single-shot `query()` THROWS after yielding an error result (error_max_turns etc.) — wrap in try/catch. If your input generator throws you get a misleading "Claude Code process aborted by user".
- `startup()` / `prewarm()` pre-spawn the CLI to hide init latency (useful for parallel DAG tasks).
- Pros: typed messages, callbacks (canUseTool, hooks as JS functions, in-process MCP), sessions helpers (`listSessions`, `getSessionMessages`, `getSessionInfo`, `renameSession`, `tagSession`, `forkSession` option), `sessionStore` to mirror transcripts to own backend, `resolveSettings`. Cons: version coupling between SDK and bundled binary; Node-only (fine for Electron main/utility).

### B. Raw CLI: `claude -p --input-format stream-json --output-format stream-json --verbose [--include-partial-messages]`
- Same protocol the SDK uses; you implement the control_request/control_response plumbing yourself. [LIVE] confirmed: with `--permission-prompt-tool stdio` the CLI emits `{"type":"control_request","request_id":...,"request":{"subtype":"can_use_tool","tool_name":"ExitPlanMode","input":{"plan":"...","planFilePath":"~/.claude/plans/xxx.md"},"tool_use_id":...,"requires_user_interaction":true}}` on stdout and waits for a `control_response`. (`--permission-prompt-tool` is hidden from `--help` but accepted; documented in cli-reference.) Only useful if you want a non-Node host or want zero SDK dependency. The control-protocol schema is not a documented stable contract -> prefer the SDK, which tracks it.
- `--output-format json` (single result) + `--json-schema` is the simplest for one-shot structured calls (plan/DAG generation, review verdicts).
- Exit codes: 0 success, non-zero on failure; SIGTERM -> 143 with no result recorded (use SIGINT or SDK `interrupt()` to end the turn gracefully).

### C. Interactive TUI in a PTY (node-pty + xterm.js)
- Gives the real Claude Code UI incl. slash commands, human takeover, plan approvals, etc. But there is no structured event stream: you'd scrape ANSI or rely on hooks/transcripts for telemetry. Fragile for automation; fine for "human takeover" view.

### Recommendation for "live + takeover-able" sessions (hybrid)
1. Run every automated task via SDK `query()` in streaming-input mode with a stable `sessionId` (you can supply `--session-id <uuid>` / `options.sessionId`), `cwd` = task worktree. Render the event stream natively in Legion's UI (this is the "live view").
2. Human takeover = (a) simple: send user messages into the same streaming input (priority `'now'` interrupts) and answer canUseTool prompts in the GUI; or (b) full takeover: `interrupt()`/`close()` the SDK process, then open an interactive `claude --resume <session-id>` in a PTY (xterm.js) with cwd = same worktree. Transcripts are shared on disk (`~/.claude/projects/<encoded-cwd>/<session-id>.jsonl`), so the TUI continues with full context. Do NOT run SDK and TUI against the same session at once: docs say resuming the same session in two terminals interleaves messages in one transcript (sessions page). Use `--fork-session` if you need a parallel copy.
3. Gotchas for resume into TUI: permission mode isn't always restored (bypassPermissions/plan not restored in terminal resume); `--mcp-config`, `--settings`, `--plugin-dir`, `--add-dir`, `--fallback-model` are NOT restored — pass again. Sessions created by `-p`/SDK are hidden from the picker and `--continue` but resumable by explicit ID.
4. Also exist (not needed, mention): `claude --bg` background sessions + `claude attach <id>`/`claude agents`/`claude logs`/`claude stop`, and Remote Control (`--remote-control`). `claude --resume <id>` of a running background session attaches to it. These are interactive-product features; I did not test them as an embedding surface. [UNVERIFIED for orchestration use]

## 2. Message stream shape  [LIVE + DOC]

Each stream-json line is one JSON object. TS `SDKMessage` union (DOC): SDKAssistantMessage, SDKUserMessage, SDKUserMessageReplay, SDKResultMessage, SDKSystemMessage (init), SDKPartialAssistantMessage (`type:"stream_event"`), SDKCompactBoundaryMessage, SDKStatusMessage, SDKLocalCommandOutputMessage, SDKHookStarted/Progress/ResponseMessage, SDKPluginInstallMessage, SDKToolProgressMessage, SDKAuthStatusMessage, SDKTaskNotification/Started/Progress/UpdatedMessage, SDKBackgroundTasksChangedMessage, SDKThinkingTokensMessage, SDKSessionStateChangedMessage, SDKWorkerShuttingDownMessage, SDKCommandsChangedMessage, SDKNotificationMessage, SDKFilesPersistedEvent, SDKToolUseSummaryMessage, SDKMemoryRecallMessage, SDKRateLimitEvent, SDKElicitationCompleteMessage, SDKPermissionDeniedMessage, SDKPromptSuggestionMessage, SDKAPIRetryMessage, SDKMirrorErrorMessage, SDKInformationalMessage, SDKConversationResetMessage.

Observed live (CLI 2.1.289):
- `system/init`: keys: cwd, session_id, tools[], mcp_servers[], model (resolved full id e.g. claude-haiku-4-5-20251001), permissionMode, slash_commands, apiKeySource, claude_code_version, output_style, agents, skills, plugins, capabilities[], memory_paths, scratchpad_path, messaging_socket_path, fast_mode_state... session_id is available here (before result) — capture it for resume.
- `system/hook_started|hook_response` (SessionStart hooks run even in -p unless --bare/--setting-sources ""), `system/status` ("requesting"), `system/post_turn_summary` (status_category, status_detail, needs_action — handy for task cards), `system/thinking_tokens`, `system/api_retry` (attempt, max_retries, retry_delay_ms, error_status, error category e.g. rate_limit/overloaded/server_error).
- `stream_event` (with `--include-partial-messages`): raw Anthropic API events: message_start (carries usage incl. cache), content_block_start (text | tool_use{id,name}), content_block_delta (text_delta | input_json_delta{partial_json} | thinking deltas), content_block_stop, message_delta (stop_reason, usage), message_stop. Main session only: subagent token deltas are NOT forwarded (parent_tool_use_id always null on stream_event).
- `assistant`: one message per completed content block (text OR tool_use), same `message.id` shared across blocks of one API response; `parent_tool_use_id` non-null for subagent messages.
- `user`: tool_result blocks (`message.content[].type=="tool_result"`, `tool_use_id`) plus `tool_use_result` convenience field; also synthetic user msgs.
- `rate_limit_event`: `rate_limit_info{status, resetsAt, rateLimitType:"five_hour", overageStatus, isUsingOverage, unifiedWindows{five_hour{utilization,resetsAt}, seven_day{...}}}` — present on subscription auth; use to throttle the DAG scheduler.
- `result`: subtype (`success`, `error_max_turns`, `error_during_execution`, `error_max_budget_usd`, `error_max_structured_output_retries`), `is_error`, `result` (text), `structured_output` (when json-schema), `session_id`, `num_turns`, `duration_ms`, `duration_api_ms`, `total_cost_usd`, `usage{input/output/cache_*}`, `modelUsage{model:{inputTokens,outputTokens,cacheRead..,cacheCreation..,costUSD,contextWindow,costBasis}}`, `permission_denials[]`, `terminal_reason` ("completed"), `stop_reason`, `subagent_stats`, `api_error_status`.
- Streaming-input mode: ONE result per user turn. Cost fields on later results are running totals for the call (don't sum); reset on /clear.

Rendering recipe: use stream_event text_delta for live text; content_block_start(tool_use)+input_json_delta for "tool running" chips; `assistant` tool_use block for final args; match `user.tool_result.tool_use_id` for completion/output; `post_turn_summary` for one-line status; `rate_limit_event`/`api_retry` for banners. Per-step `output_tokens` on assistant messages is a placeholder; use result usage. Dedupe usage by `message.id`. `total_cost_usd` is a client-side ESTIMATE (do not bill from it).

Observation [LIVE]: a trivial "hi" with the user's full config cost ~$0.17 and ~41k cache-creation tokens (system prompt + this machine's many MCP servers/skills). With `--strict-mcp-config --setting-sources "" --disable-slash-commands` it was still ~35k tokens ($0.075 on haiku). Orchestrator should pass minimal MCP/settings for sub-tasks and prefer `--bare`-like isolation (see §6).

## 3. Permissions / approvals

Permission modes (CLI `--permission-mode` choices verified): `acceptEdits`, `auto`, `bypassPermissions`, `manual` (CLI name; SDK type calls it `default`), `dontAsk`, `plan`. SDK `PermissionMode` = default | acceptEdits | bypassPermissions | plan | dontAsk | auto.
- NOTE: since TS SDK v0.3.286 omitting `permissionMode` no longer means `default`; it follows settings/built-in default which can be `auto` (model-classifier approvals). Always pass it explicitly.
- Evaluation order: PreToolUse hooks -> deny rules (disallowedTools/settings) -> ask rules -> permission mode -> allow rules (allowedTools/settings) -> `canUseTool` callback. `dontAsk` skips callback and denies. `permissionPrompts: 'none'` (CLI `--permission-prompts none`, v2.1.259+) denies anything that would prompt (good for unattended tasks). `permissionPromptToolName` routes prompts to an MCP tool instead of canUseTool.
- `canUseTool(toolName, input, {signal, suggestions, blockedPath, decisionReason, toolUseID, agentID, requestId, ...})` -> `{behavior:'allow', updatedInput?, updatedPermissions?}` | `{behavior:'deny', message, interrupt?}`. Can stay pending indefinitely (GUI approval dialog). For long waits use a PreToolUse hook returning `permissionDecision:'defer'` -> turn ends with `stop_reason:"tool_deferred"`, resume later from persisted session.
- GOTCHA: allow rules, `acceptEdits`, `bypassPermissions` resolve BEFORE canUseTool, so canUseTool never sees auto-approved calls. SDK warns (`CLAUDE_SDK_CAN_USE_TOOL_SHADOWED`). For global audit/telemetry use PreToolUse hook. `allowedTools` does NOT restrict `bypassPermissions`; use `disallowedTools` (bare name removes tool from context; scoped `Bash(rm *)` denies matches even in bypass). `tools:[...]` restricts built-ins (include `AskUserQuestion` if you want questions).
- `AskUserQuestion` arrives through canUseTool: input `{questions:[{question, header, options:[{label,description,preview?}], multiSelect}]}`; reply by allow with `updatedInput:{questions, answers:{[questionText]: label|labels}}` (optional `response` freeform). Not available inside subagents.
- GUI surfacing: canUseTool -> push IPC to renderer with {requestId, toolName, input, suggestions, decisionReason}; renderer returns decision; "always allow" = echo a suggestion with destination `localSettings` back in `updatedPermissions`. Also `PermissionRequest` and `Notification(permission_prompt)` hooks for notifications. `SDKPermissionDeniedMessage` / `permission_denials` in result for audit.
- bypassPermissions: refuses to run as root outside sandbox; subagents inherit it. Recommend: sandbox via worktree + `acceptEdits` + curated allowedTools (`Bash(git *)`, test commands) + `dontAsk` for headless tasks, rather than bypass. SDK also has `sandbox` option [DOC; details not verified].

## 4. Plan mode & structured output

Plan mode: `permissionMode:'plan'` (CLI `--permission-mode plan`). Read-only exploration; edits/shell writes prompt via canUseTool. Claude ends by calling the `ExitPlanMode` tool; [LIVE] it surfaced as a can_use_tool control_request with `input:{plan:"<markdown>", planFilePath:"~/.claude/plans/<slug>.md"}` and `requires_user_interaction:true`. If you deny/ignore, the result lists it in `permission_denials` with the plan in `tool_input.plan` — so even a headless run can harvest the plan text. Approve (`allow`) => leaves plan mode and Claude proceeds to implement; deny with message => Claude revises. Plan mode may also call AskUserQuestion. `planModeInstructions` option customizes the workflow. Model alias `opusplan` = Opus for planning, Sonnet for execution. Also note plan mode writes a plan file under `~/.claude/plans/` even though source edits are blocked.
 [UNVERIFIED]: exact TS type name/shape of ExitPlanMode input in the SDK reference (docs excerpt was truncated); the live JSON above is authoritative for 2.1.289.

Structured output (for the task DAG): `options.outputFormat = {type:'json_schema', schema}` (CLI: `--output-format json --json-schema '<schema>'`). Result has `structured_output`; failure = subtype `error_max_structured_output_retries` (or success with no structured_output — treat as failure). [LIVE]: implemented via an injected `StructuredOutput` tool; CLI re-prompts "[structured-output-enforce] You MUST call the StructuredOutput tool" and validates, so it is multi-turn (extra cost: 3 turns for "hi"). JSON Schema draft-07 only (Zod: `z.toJSONSchema(s,{target:'draft-7'})`); `format` is annotation only; invalid schema fails at startup (v2.1.205+). Works with tool use before the final answer, so one agent can explore the repo AND emit the DAG. Keep schema shallow; validate again with Zod on your side (DAG acyclicity, id refs).
Recommended two-stage: (1) plan-mode session produces markdown plan (ExitPlanMode); (2) same session resumed (or new, with plan text) with outputFormat to convert plan -> DAG JSON {tasks:[{id,title,description,deps[],files[],acceptance[]}]}.

## 5. Sessions

- Session id: in `system/init.session_id` and every message/result. You can assign: `options.sessionId` (UUID) / CLI `--session-id`.
- Resume: `options.resume=<id>` (CLI `-r/--resume`), continue most-recent-in-cwd: `continue:true` (`-c`). Fork: `forkSession:true` with resume (CLI `--fork-session`) -> new id, original untouched (history only, NOT filesystem). `resumeSessionAt` (message uuid) and `resumeDropsTurn` for partial rewind; `rewindFiles(userMessageId)` + `enableFileCheckpointing` for file rewind.
- Lookup: id searched in current project dir + its git worktrees, then all projects (v2.1.223+); fails if duplicates. `--resume <path/to/file.jsonl>` also works.
- Transcripts: `~/.claude/projects/<cwd with non-alnum -> '-'>/<session-id>.jsonl` (`$CLAUDE_CONFIG_DIR/projects/...` if set; >200 chars truncated+hash). Entry format is internal and unstable — read via `getSessionMessages()` / `listSessions()` instead. 30-day default retention (`cleanupPeriodDays`). Multi-tenant hosts: `CLAUDE_CONFIG_DIR` + `CLAUDE_CODE_PROJECT_DIR_NAME` (v2.1.234+). `persistSession:false` / `--no-session-persistence` for ephemeral. `sessionStore` adapter mirrors transcripts to your DB (cross-host resume).
- Worktree interplay: transcripts are keyed by cwd. If a task worktree is deleted and you later resume, Claude Code resumes in the current dir; keep worktrees until the task is done, or pass `CLAUDE_CODE_PROJECT_DIR_NAME` for stable keying.
- Interrupt: `await q.interrupt()` (returns receipt with still_queued/cancelled uuids, v2.1.219+) ends the current turn but keeps the process/session; `abortController` / `q.close()` kills the process. Pending hook/permission callbacks are cancelled on interrupt (v2.1.208+). CLI: SIGINT ends turn; SIGTERM leaves turn unfinished (exit 143).
- Mid-run injection: with streaming input, yield another `SDKUserMessage` with `priority:'now'` (interrupt and read immediately) | `'next'` (default; picked up in same turn after tools finish) | `'later'` (after turn ends -> new turn). `q.streamInput()` also exists. CLI: write another `{"type":"user",...}` line to stdin; `--replay-user-messages` echoes acks.
- Background tasks at exit: in `-p`, background Bash is killed ~5s after final result; background subagents/workflows/Monitor keep process open up to 10 min (`CLAUDE_CODE_PRINT_BG_WAIT_CEILING_MS`).

## 6. Working dir, worktrees, settings, hooks

- `options.cwd` (CLI: process cwd). `additionalDirectories` / `--add-dir` for extra readable/writable dirs (not restored on resume). CLI has `-w/--worktree [name]` (creates a git worktree for the session) and SDK hooks `WorktreeCreate/WorktreeRemove`; EnterWorktree/ExitWorktree tools exist. Legion should create worktrees itself (git worktree add per DAG task, branch per task) and set `cwd`; that gives deterministic paths + merge control. `claude -w` is an alternative but you lose control of location/branch naming. [`--worktree` semantic details UNVERIFIED]
- Settings sources: `settingSources: ['user','project','local']` (CLI `--setting-sources user,project,local`). In the SDK, default `query()` loads project settings (CLAUDE.md, .claude/settings.json, skills, commands, hooks, .mcp.json); pass `[]` for isolation. `settings` option (inline object/path) and `managedSettings` (policy tier) give programmatic config. `resolveSettings()` shows effective/provenance. `--bare` (CLI) skips hooks, LSP, plugins, auto-memory, CLAUDE.md discovery, keychain/OAuth (API-key ONLY) — docs say it will become the default for -p. `--safe-mode`, `--restricted` also exist. NOTE `-p` skips workspace trust dialog and runs project hooks/.mcp.json of an untrusted repo — security consideration for Legion on arbitrary repos (use `--bare`/settingSources:[] + explicit config for untrusted repos).
- `systemPrompt: {type:'preset',preset:'claude_code', append:'...'}` (CLI `--append-system-prompt`); `--exclude-dynamic-system-prompt-sections` improves cache reuse across worktrees.
- Hooks: SDK callback hooks (`options.hooks`) AND shell-command hooks in settings. TS events: PreToolUse, PostToolUse, PostToolUseFailure, PostToolBatch, UserPromptSubmit, UserPromptExpansion, MessageDisplay, Stop, StopFailure, SubagentStart, SubagentStop, PreCompact, PostCompact, PreModelSwitch, PostModelSwitch, PermissionRequest, PermissionDenied, SessionStart, SessionEnd, Notification, Setup, TeammateIdle, TaskCreated, TaskCompleted, Elicitation, ElicitationResult, ConfigChange, InstructionsLoaded, WorktreeCreate, WorktreeRemove, CwdChanged, FileChanged, DirectoryAdded. (Python lacks several.) Callback `(input, toolUseID, {signal}) => Promise<output>`; matcher is a tool-name regex/pipe list; input carries session_id, cwd, hook_event_name, agent_id/agent_type; output `{hookSpecificOutput:{hookEventName, permissionDecision:'allow'|'deny'|'ask'|'defer', permissionDecisionReason, updatedInput, additionalContext, updatedToolOutput}, systemMessage, continue}`; `{async:true}` for fire-and-forget telemetry. Multiple hooks run in parallel; deny > defer > ask > allow. Default timeout 600s (30s UserPromptSubmit). `includeHookEvents:true` puts hook lifecycle into stream.
- Telemetry plan: PostToolUse (async) for file-change audit/diff tracking; `Stop`/`SubagentStop` as "agent finished" signals (can also return a block decision to force more work — e.g. "run tests before stopping"); `TaskCompleted`/`TaskCreated` track TaskCreate tool use; `Notification`; `FileChanged`. PreToolUse can enforce worktree boundaries (deny writes outside cwd) beyond `additionalDirectories`.
- The older docs' claim of hook events like "PreMessageSend/PostMessageReceive" that one summarizer returned is NOT in the hooks page; ignore.

## 7. MCP

- `options.mcpServers: Record<string, McpServerConfig>` — stdio `{command,args,env}`, `{type:'sse'|'http', url, headers}`, or in-process `createSdkMcpServer({name, version, instructions, tools:[tool(name, desc, zodShape, handler, {annotations, alwaysLoad})]})` (type "sdk"; runs inside the host process — i.e. inside Legion's main/utility process, so handlers can touch app state directly). CLI equivalents: `--mcp-config <json|file>...`, `--strict-mcp-config` (ignore all other MCP config).
- Tool names: `mcp__<serverKey>__<tool>`; pre-approve via `allowedTools` (supports `mcp__server__*`; no unanchored globs). Handler returns `{content:[{type:'text'|'image'|'resource'|'resource_link'|'audio'}], structuredContent?, isError?}` (Python drops structuredContent). Uncaught exceptions become error tool results. Per-server `timeout` (v0.3.248+). Tool search (deferral) is on by default for SDK MCP tools; `alwaysLoad:true` keeps schema in prompt.
- Orchestrator tools to expose (suggested): `report_progress({taskId, percent, note})`, `request_human_input({question, options?})` (handler awaits GUI response -> returned as tool result; alternative to AskUserQuestion that also works inside subagents), `mark_task_done({summary, filesChanged, followUps})`, `submit_plan`/`submit_dag`, `submit_review({verdict, findings[]})`. Mark side-effect-free ones `readOnlyHint`. Add `Stop` hook guard: if mark_task_done wasn't called, return `continue`/block with a reminder.
- MCP elicitation: `onElicitation` callback option + Elicitation hooks.
- Verification: in `system/init`, check `mcp_servers[].status` and `mcp_server_errors` (invalid entries are silently skipped). Remote servers with cached tool lists may show `pending` and connect on first call.
- In-process SDK servers require streaming-input mode? Docs for custom-tools don't state it explicitly; the permission/hook doc notes only that canUseTool needs an open stream in Python. In TS, passing a string prompt with sdk MCP works in the doc examples. [LOW RISK; not tested]

## 8. Subagents, models, effort, cost, rate limits

- Subagents: `agents: Record<string, AgentDefinition>` {description, prompt, tools, disallowedTools, model, mcpServers, skills, maxTurns, background, permissionMode, effort, memory, initialPrompt, omitClaudeMd}; CLI `--agents <json|file>`; `agent` option / `--agent` picks main-thread agent. Built-in Agent/Task tool spawns them. Subagent msgs carry `parent_tool_use_id` (nested to any depth); `forwardSubagentText`/`--forward-subagent-text` forwards their text/thinking (v2.1.211+); `agentProgressSummaries`; hooks SubagentStart/Stop; `result.subagent_stats` and caps for depth/concurrency/spend. Subagent permission mode inherits parent; bypassPermissions can't be set per-agent. AskUserQuestion unavailable in subagents. Stream token deltas not forwarded for subagents. Legion should still do its own DAG parallelism by separate `query()` processes per task (isolation + per-task budget), not Claude subagents; use subagents inside a task (e.g. explore/review).
- Models: `--model`/`options.model` aliases: `default`, `best`, `fable`, `opus` (Opus 5.5 on API), `sonnet` (Sonnet 5.5), `haiku`, `sonnet[1m]`, `opus[1m]`, `opusplan`, or full ids. [LIVE] `--model haiku` resolved to claude-haiku-4-5-20251001 (init.model). `fallbackModel`/`--fallback-model a,b`; `CLAUDE_CODE_SUBAGENT_MODEL`; `ANTHROPIC_DEFAULT_{OPUS,SONNET,HAIKU,FABLE}_MODEL` pins; `q.setModel()` mid-session; `supportedModels()`. Auto fallback on safety-classifier flags (Sonnet 5.5 security flag -> Sonnet 5, biology flag -> refusal) toggle `switchModelsOnFlag`.
- Effort: `effort: 'low'|'medium'|'high'|'xhigh'|'max'` / `--effort` / `CLAUDE_CODE_EFFORT_LEVEL`; per-agent `effort`; `applyFlagSettings({effortLevel})`. Thinking: `thinking: {type:'adaptive'|'enabled',budgetTokens|'disabled'}` (`maxThinkingTokens` deprecated); can't disable on Opus 5.5/Sonnet 5.5/Fable.
- Budget/limits: `maxTurns`, `maxBudgetUsd` (`--max-budget-usd`, -p only; counts only this call's own spend), `taskBudget{total}` (API-side tokens), `autocompact`.
- Cost: result `total_cost_usd` + `modelUsage` (includes subagents; `usage` excludes them). Estimates only. Resumed sessions report cumulative spend since v2.1.277 (don't sum across resumes). On subscription auth cost is notional (not billed per token) — still useful for relative budgeting.
- Rate limits: `rate_limit_event` messages (status, resetsAt, rateLimitType five_hour/seven_day, utilization 0..1, overage info) — use to pause scheduler / lower parallelism; `system/api_retry` shows automatic retries (error `rate_limit`/`overloaded`); `CLAUDE_CODE_MAX_RETRIES`, `API_TIMEOUT_MS`, `CLAUDE_ASYNC_AGENT_STALL_TIMEOUT_MS` env via `options.env`. Result may be `is_error` with `api_error_status` 429 after retries. [Exact subscription-limit-hit result shape UNVERIFIED — I did not exhaust a limit.]
- Prompt cache: 1h TTL on subscription within plan usage; with API key default 5m -> set `ENABLE_PROMPT_CACHING_1H=1` for long DAG runs. ~35-41k token baseline per fresh session => parallel sessions with identical system prompt benefit from cache; `--exclude-dynamic-system-prompt-sections` + identical settings improves reuse.

## 9. Auth & ToS  (IMPORTANT for Legion)

- Local state [LIVE]: `claude auth status` -> loggedIn, authMethod "claude.ai" (subscription OAuth), apiProvider firstParty. `claude auth login/logout/status`, `claude setup-token` (long-lived token, requires subscription) exist. Result `apiKeySource` in init shows which credential is used. Env: `ANTHROPIC_API_KEY`; Bedrock/Vertex("Google Cloud's Agent Platform")/Foundry via `CLAUDE_CODE_USE_BEDROCK` etc.
- Both the SDK and `claude -p` technically work with the logged-in subscription (the SDK spawns the same binary and inherits OAuth/keychain), EXCEPT `--bare` (API key / apiKeyHelper only; never reads OAuth/keychain) and `ultrareview`/cloud features (claude.ai login required; not on Bedrock/Vertex/Foundry/ZDR).
- Policy (docs, verbatim gist): Agent SDK overview: "Unless previously approved, Anthropic does not allow third party developers to offer claude.ai login or rate limits for their products, including agents built on the Claude Agent SDK. Use API key authentication." Legal page: OAuth is for ordinary use of Claude Code and native Anthropic apps; developers building products (incl. via Agent SDK) should use API keys (Console) or cloud-provider creds; no third-party "Login with Claude", no routing requests via Free/Pro/Max credentials on behalf of users, no collecting/storing/intermediating claude.ai credentials or session tokens. BUT: "Nor does it prevent an end user from signing in to the unmodified Claude Code binary with their own Claude subscription, including where a platform hosts Claude Code" and customers may run Claude Code in their products if binary unmodified, auth methods not removed/restricted, and each end user authenticates with their own key/plan (no reselling/paying on behalf). Pro/Max advertised limits assume "ordinary, individual usage of Claude Code and the Agent SDK". Enforcement may occur without notice.
- Practical reading for Legion (local single-user desktop app; I am not a lawyer): SAFE: user provides their own `ANTHROPIC_API_KEY` (or Bedrock/Vertex creds) -> use SDK. GREY: Legion spawning the unmodified `claude` binary (via CLI or SDK-bundled binary) that is already logged in with the user's own subscription, with Legion never touching tokens/never implementing a login UI. Closest-to-compliant subscription path = drive the user's own installed/unmodified `claude` via `pathToClaudeCodeExecutable`/CLI and tell the user to run `claude auth login` themselves (Legion must not collect OAuth creds or offer "Sign in with Claude"); heavy parallel automation on a Pro/Max plan may exceed "ordinary individual usage" and hit limits. Recommend: support API key as first-class, subscription as "bring your own logged-in Claude Code" with a disclosure, and confirm with Anthropic (sales contact) if distributing broadly. Branding: don't name product "Claude Code"; permitted: "Claude Agent", "{YourAgentName} Powered by Claude"; no Claude Code-like ASCII/visuals.
- Cost caveat on subscription: `rate_limit_event.isUsingOverage` / overageStatus; extra usage credits can be consumed.

## 10. Headless code review

- `/code-review` (alias `/review` since v2.1.223): local diff review (branch commits ahead of upstream + uncommitted; targets: path, PR number, branch, `main...feature`). Flags `--fix`, `--comment` (GitHub inline comments / GitLab note via glab), `--max-findings <n|all|default>` (v2.1.288+), effort level arg low..max (low/medium = fewer high-confidence findings). In `claude -p` it runs foreground and returns findings as TEXT in the reply (skills with `/skill-name` in prompt expand in -p). Desktop host gets structured `ReportFindings` tool (a tool is in the init tool list [LIVE]) when host requests findings list (v2.1.218+) — a custom host *might* be able to request this; mechanism not documented here [UNVERIFIED].
- `claude ultrareview [target] [--json] [--post|--no-post] [--timeout 45]` [help verified LIVE]: cloud-hosted multi-agent review of current branch / PR / base branch, prints findings; `--json` prints raw bugs.json. Requires claude.ai auth (not API-key-only/3P/ZDR), billed via usage credits per docs (managed Code Review ~$15-25 per review avg; ultrareview pricing page not checked). Uploads repo to cloud. Good optional "deep review" for final PR.
- Managed GitHub "Code Review" (Team/Enterprise): @claude review on PR; check run output machine-readable severity; REVIEW.md customizes. `claude-code-action` GitHub Action and GitLab CI also exist. `/security-review` is a bundled skill too (listed in this session's skills).
- For Legion's per-task review step prefer a custom review: a fresh `query()` (new session, read-only tools `['Read','Grep','Glob','Bash(git diff *)']`, `permissionMode:'dontAsk'`/plan) with a review system prompt + `outputFormat` schema `{verdict, findings:[{file,line,severity,message}]}`. This gives backend-parity with Codex (same schema, same prompt) and structured output; `/code-review` via `-p` returns prose only.

## Cross-cutting design notes for Legion's backend abstraction
- Normalize to an `AgentRun` interface: start({cwd, prompt, schema?, mode: plan|execute|review, model, effort, budget}), events (text-delta, tool-start, tool-end, approval-request, question, progress, usage, rate-limit, done), `send(msg, priority)`, `interrupt()`, `resume(sessionId)`, `fork()`. Claude maps 1:1 onto SDK; keep `sessionId` + `cwd` + backend in persistent task state.
- Approvals: unify Claude canUseTool and Codex approval requests into one GUI approval object (tool, input preview, suggestions).
- Run SDK in an Electron utilityProcess (not renderer, not main) — one process per active query; each spawns a `claude` child (~35-40k token baseline, ~hundreds of MB RAM each) => cap concurrency.
- Pin Claude Code version (bundled with SDK; SDK 0.3.x tracks CLI 2.1.x). The SDK + CLI evolve quickly (many "requires vX" notes); feature-detect through `system/init.capabilities` rather than versions.
- Unverified / not tested: Windows behavior; Remote Control / `--bg` as embedding; `sandbox` options; exact Electron packaging of the native binary (asar unpack needed — [UNVERIFIED]); behavior when two processes resume same session; subscription-limit-exhausted result shape; `ExitPlanMode` approval semantics in SDK (approve => auto leave plan, mode switching) beyond the observed control_request.
