## 1. Build/packaging/update
- electron-vite 5 (Vite-based, main/preload/renderer in one config, HMR for renderer, preload reload) is what both leading apps use. Forge 8 + Vite plugin is viable and official but the Vite plugin has historically lagged; electron-builder 26.x remains the pragmatic packager (dmg/zip/nsis/AppImage, notarize hooks, electron-updater integration, differential updates).
- Recommend: electron-vite 5 + electron-builder 26 + electron-updater 6.8 against GitHub Releases (or S3/R2). update.electronjs.org is only for public GitHub repos w/ Forge-style zips; fine for OSS, but electron-updater gives staged rollouts/channels (Emdash uses canary yml). macOS: Developer ID cert + notarization via @electron/notarize (or builder's `notarize`), hardened runtime + entitlements (allow-jit, allow-unsigned-executable-memory for V8; disable-library-validation only if needed). Must ship both arm64 and x64 (or universal) and asarUnpack native modules (.node, node-pty spawn-helper). Auto-update on macOS requires signed zip + dmg.
- Monorepo: pnpm workspaces + (turbo or nx); Biome or oxlint.

## 2. Process architecture
- Electron main = thin: windows, menus, tray, notifications, protocol, safeStorage, updater, powerSaveBlocker. Never run agent loops or git in main.
- Put the **orchestrator engine in a long-lived Node process, not in the renderer and not in main**: use `utilityProcess.fork` (Chromium-managed Node child, supports MessagePort to renderer directly, crash isolation, restartable, can load native addons, `serviceName` shows in Activity Monitor). Pattern: main spawns "engine" utilityProcess; hands the renderer a MessagePort via `webContents.postMessage`; renderer talks to engine directly (main out of hot path).
- Agent sessions: Claude Agent SDK / Codex SDK spawn their own CLI child processes anyway, so the engine mostly handles streams. Optionally shard: one utilityProcess for engine+DB+git, one "pty-host" for node-pty (Superset has a standalone pty-daemon so terminals survive app restarts/crashes - copy this idea; a detached daemon via unix socket is the strongest option for "agents keep running when UI closes"). Worker threads fine for CPU tasks (diff parsing, DAG layout via elkjs worker, big JSON parsing) but native addons + worker threads is fragile; keep better-sqlite3 in the engine's main thread (sync, fast) or a dedicated writer.
- Design engine as transport-agnostic (JSON-RPC-ish, event-sourced) so it can later run headless/remote (Emdash's SSH hosts; Superset's relay) and under Node tests without Electron.
- Crash isolation: supervisor in main restarts the engine, engine rehydrates from SQLite event log; sessions identified by generation fence (Emdash pattern).

## 3. Type-safe IPC
- Options: trpc-electron 0.1.2 (maintained fork; Superset uses; supports subscriptions over ipc), electron-trpc 0.7.1 (stale), @egoist/tipc 0.4.0 (tiny, no real subscriptions story), oRPC 1.15 (modern, typed contracts, streaming via async iterators, works over MessagePort adapters - (unverified) has message-port adapter), hand-rolled typed contextBridge.
- Recommend: **oRPC or tRPC v11 over a custom MessagePort link** between renderer and engine utilityProcess (not through main ipcMain), with async-iterator subscriptions. If wanting zero risk, trpc-electron is proven in Superset. Regardless: batch high-frequency agent events engine-side (coalesce to ~16-50ms frames, send arrays), sequence numbers + resume-from-cursor so renderer can catch up after reload, zod/valibot schemas shared in a `@legion/protocol` package. Raw PTY bytes: separate dedicated MessagePort per terminal (or binary transfer w/ ArrayBuffer transfer), bypass RPC serialization. structuredClone over MessagePort is fast; avoid JSON strings.
- Keep contextBridge minimal: expose only `connectEngine()` that returns the port, plus a few main-process verbs (dialogs, notifications). contextIsolation on, sandbox on, nodeIntegration off.

## 4. Persistence
- better-sqlite3 13.0.3: fastest sync API, prebuilt binaries for Electron lag at times; needs `electron-rebuild`/builder `npmRebuild` + asarUnpack. Used by all three OSS apps. node:sqlite (built in; Electron 44 bundles Node 24-ish (unverified) so available; still release-candidate/experimental-ish API, no prebuild pain, fewer features/perf tuning) - tempting for zero native rebuilds; Drizzle driver support for node:sqlite is newer (unverified). libsql 0.5: native too, adds sync/replication only useful for cloud sync.
- Recommend: **better-sqlite3 + Drizzle ORM (0.45) + drizzle-kit migrations** (Kysely 0.29 is a fine alternative if you prefer SQL-first typing; Drizzle has the schema-first migration flow and matches OSS precedent). Run it in the engine utilityProcess only. PRAGMAs: journal_mode=WAL, synchronous=NORMAL, busy_timeout, foreign_keys=ON, wal_autocheckpoint tuned.
- Event logs: append-only `events(session_id, seq, ts, type, payload JSON/BLOB)` with index (session_id, seq); batch inserts in a transaction every ~50-100ms; store big blobs (tool outputs, diffs, terminal scrollback) as files in app data dir, or compressed (zstd/brotli via zlib) rows, referenced by hash; keep derived/projection tables for UI (task status, DAG) rebuilt from events. Periodic retention/vacuum. Consider also keeping the CLI's own transcripts (~/.claude, ~/.codex) as source of truth for resume.

## 5. Terminal
- node-pty 1.1.0 (Microsoft; Superset on 1.2 beta) + @xterm/xterm 6.0 (6.x moved addon scopes to @xterm/*; removed canvas renderer; DOM+WebGL only). Addons: fit, webgl (with context-loss fallback), serialize, search, unicode11 (or unicode-graphemes), web-links, clipboard, image optional.
- Many terminals: WebGL contexts are limited (~16 per page in Chromium) - only attach the WebGL addon to the visible/focused terminal, dispose when hidden; keep non-visible sessions as **@xterm/headless** instances in the engine (or renderer) that parse the stream and can `serialize()` the screen + scrollback to hydrate an xterm when user opens/takes over. Backpressure: write callbacks/flow control (pause pty when xterm write queue > watermark). Scrollback 5-10k lines. Run PTY in separate process (daemon) as above. Cross-platform: node-pty uses ConPTY on Windows; ship prebuilds (node-pty 1.x has prebuilds) and asarUnpack spawn-helper.
- Structured sessions via SDK and the PTY are different modes: model "session" with transport = sdk | pty; takeover = resume same session id in the CLI inside a PTY.

## 6. UI
- React 19 + Vite + Tailwind v4 (@tailwindcss/vite). Components: shadcn/ui on Radix (radix-ui 1.7 unified pkg) or on **Base UI** (@base-ui/react 1.8, now stable; Emdash uses it; shadcn supports Base UI variant) - for new build pick Base UI primitives via shadcn for long-term maintenance (Radix maintenance slowed) or Radix for maximal ecosystem; either OK.
- State: server-ish data (sessions, tasks) = TanStack Query w/ engine subscriptions writing into the cache, or a store fed by subscriptions; local UI state = Zustand 5 (Superset) or Jotai 3 for fine-grained atoms (good for per-session timeline slices). Avoid global re-renders from event stream: normalized store + selector subscriptions, `useSyncExternalStore`. MobX is Emdash's choice. Recommend Zustand (+immer sparingly) + TanStack Query for request/response; TanStack Router for typed routes (or none: a panel/tab layout state machine).
- cmdk 1.1.1 command palette; global keybinding registry (e.g., tinykeys / @tanstack/hotkeys (unverified)) with a single command registry feeding palette, menus, tooltips. Layout: resizable panels (react-resizable-panels), tabs/splits.
- TanStack Virtual 3.14 for timelines (dynamic row measurement; stick-to-bottom logic; handle streaming growth). Motion 14 (formerly framer-motion) for micro-interactions; respect prefers-reduced-motion; animate transform/opacity only.
- Perf musts: React Compiler (stable) on; avoid re-rendering whole timeline per token; render streaming message in its own component; content-visibility for offscreen.

## 7. DAG
- @xyflow/react 12.12 is the default: custom nodes (React), minimap, handles, edge reconnect, virtualization (`onlyRenderVisibleElements`). Layout: **elkjs 0.12** (layered, handles ports/clusters, run in web worker) or @dagrejs/dagre 3.1 (simple, fast, synchronous; fine for <200 nodes). Recommend dagre first, ELK if you need compound nodes/ports; animate position changes via CSS transitions. Alternatives: Cytoscape (graph analysis, less React-friendly), Rete.js, tldraw (canvas), custom SVG for read-only. Keep graph model in your store, React Flow as a view.

## 8. Diff/code review
- @pierre/diffs 1.5.2 (Pierre's diff/file renderer; Superset uses it; Shiki-based, virtualized, annotations/inline comment slots, split/unified, worker-pool highlighting) - best fit for review UI with inline comments and big diffs; younger library, check license/API stability. Monaco 0.57 diff editor: richest (full editor, minimap) but heavy (~MBs, workers, theming mismatch, awkward inline-comment widgets via zones; Emdash uses). CodeMirror 6 @codemirror/merge 6.12: lightweight, themeable, good for editable diffs and file editing (Superset uses CM6 for file editing); inline comment widgets possible via decorations. react-diff-view / diff2html: simpler, less polished; diff2html static HTML.
- Recommend: @pierre/diffs for review (read-mostly with comment annotations), CodeMirror 6 for in-app file editing/conflict resolution; fall back to Monaco only if full IDE features demanded. Syntax highlighting: Shiki 4.5 with the oniguruma-WASM or JS engine, highlight in a worker, lazy-load grammars, theme matching app tokens. Large diffs: collapse by default over N lines, virtualize file list + hunks, compute diffs in git (`git diff --patch`/numstat) in engine, not in JS.

## 9. Markdown/plan editing
- Agent output: **streamdown 2.7** (Vercel; built for streaming, handles unterminated blocks, shiki code blocks, memoized per-block) vs react-markdown 10.1 (+remark-gfm, rehype; re-parses whole message unless you memoize by block). Recommend streamdown or react-markdown with block-level memoization (split by top-level blocks, only last re-renders). Sanitize (rehype-sanitize); links open via shell.openExternal.
- Plan editor: TipTap 3.31 (ProseMirror, rich, collaborative-ready; Superset uses TipTap + tiptap-markdown) vs Milkdown 7.22 (ProseMirror + remark, markdown-native) vs CodeMirror 6 markdown (source-mode, fastest, best for power users). Since plan is likely markdown/structured tasks, recommend TipTap (WYSIWYG-ish, slash menu, task-list nodes, custom node for "task block" linked to DAG) with a toggle to raw CM6 markdown. Keep canonical form as markdown/JSON schema validated.

## 10. Git and GitHub
- Shell out to the system `git` (via execa/`child_process` in the engine) with `--porcelain=v2 -z`, `worktree` commands, `cat-file --batch` for hot paths; this is the most compatible and fast. simple-git 4.0.2 is a thin wrapper (Superset uses) - fine but adds little; isomorphic-git 1.43 lacks worktree support and is slow - avoid. dugite 3.2.3 bundles git binary (GitHub Desktop) - consider only for consistent git version on Windows/no-git machines (adds ~50-100MB per platform). Recommend: system git w/ minimum version check, optionally dugite fallback later. Git worktrees per task = isolation primitive; use a mutex per repo for index.lock-sensitive ops; use `git status` via fs watcher (@parcel/watcher) debounce.
- GitHub: Octokit (octokit 5 / @octokit/rest 22) + @octokit/auth-oauth-device for device flow (Emdash does exactly this) - store token via safeStorage. Also detect and reuse `gh auth token` if gh installed. `gh` CLI is convenient for PR create but is external dependency; Octokit for structured data (checks, reviews, GraphQL). Recommend Octokit primary, gh token piggyback.

## 11. Native niceties
- Notification (Electron `Notification`, with actions on macOS; click focuses the session), dock badge (`app.dock.setBadge`, `app.setBadgeCount`), Tray/menu-bar status item with running-agent count + quick popover window, `globalShortcut.register` for summon/quick-composer, deep links via `app.setAsDefaultProtocolClient('legion')` + `open-url` (macOS) / second-instance (Win/Linux), `powerSaveBlocker.start('prevent-app-suspension')` while any agent running (note: 'prevent-display-sleep' not needed), `safeStorage` (Keychain-backed) for tokens/API keys (check `isEncryptionAvailable`; on Linux needs libsecret), `nativeTheme`, vibrancy (`vibrancy: 'sidebar'`, titleBarStyle 'hiddenInset' + trafficLightPosition) for macOS-native feel, `app.requestSingleInstanceLock`, window state persistence, Spotlight-like quick window. Utility process should not call Electron UI APIs; route via main.

## 12. Testing
- Vitest 5 (unit; engine logic runs in plain Node; Emdash also uses Vitest browser mode with Playwright for component tests), @playwright/test 1.63 with `_electron.launch` for e2e (Playwright's Electron support is still marked experimental). Use fake agent (scripted SDK/CLI stub emitting recorded event streams) for deterministic e2e; recorded fixtures of real Claude/Codex events. Storybook for components (Superset). Test engine against a real temp git repo.

## 13. Agent SDK integration notes
- @anthropic-ai/claude-agent-sdk 0.3.292 (TS, spawns bundled claude CLI, streaming input, hooks, permission callbacks, resume/fork); @openai/codex-sdk 0.160.1 (wraps codex CLI over JSONL) and `codex app-server` JSON-RPC (richer: approvals, turn items, thread resume) - prefer app-server for Codex. Superset also uses ACP adapters (@agentclientprotocol/claude-agent-acp 0.85, codex-acp 2.1): one protocol (Agent Client Protocol) for both agents is an option to unify the adapter layer; evaluate vs native SDKs (SDK = more features, ACP = uniform). Both CLIs must be spawned from engine with correct PATH (GUI apps on macOS don't inherit shell env: resolve via login-shell `$SHELL -ilc env`, e.g. shell-env/fix-path).
